# Engineering Governance v0.5.0 Minimal Navigation + Follow-ups Implementation Plan

> Historical execution note (2026-10-10): this plan records the original v0.5 Navigation + Follow-ups construction path. Its sequencing around `NO_MERGE`, `NO_RELEASE`, and local V1 before release is superseded by `EG-V0.5-STORAGE-INTEGRATION-CLEAN-BASELINE-049`, which integrates Storage Affinity, creates one clean main baseline, and defers local installation/behavior testing until after that integration and lifecycle closeout. The reusable Navigation/Follow-up semantics below remain valid inputs to the integrated candidate.

> **For agentic workers:** use the repository's accepted execution method. Remote Tasks 1–5 are executed natively through the GitHub connector and must not depend on local worktrees, shell-only scripts, or subagent machinery. Local acceptance begins only after the remote source-audit gate.

**Goal:** Make verified navigation corrections persist into the existing derived map, and make small non-blocking adjacent problems visible in `CURRENT_STATUS.md` so they can be considered when choosing the next task.

**Architecture:** Keep the existing three-Skill model and three-file project control plane. Domain Navigation updates only verified affected routing claims. Project Governance uses a small optional `CURRENT_STATUS.md / Follow-ups` section instead of a new Findings registry or external tracker framework.

**Tech Stack:** Markdown Skill contracts/templates, JSON Plugin metadata, Git/GitHub controls.

**Spec:** `docs/superpowers/specs/2026-10-09-navigation-learning-deferred-findings-v0.5.0-design.md`

## Global Constraints

- Keep exactly three Skills: `project-governance`, `domain-navigation`, `incident-doctor`.
- Keep global Router semantics unchanged.
- Keep exactly the existing three project controls: `AGENTS.md`, `CURRENT_STATUS.md`, `CURRENT_TASK.md`.
- `CURRENT_TASK.md` remains the only execution authorization for product/task work.
- `CURRENT_STATUS.md` remains a current snapshot, not a backlog/history database.
- Navigation projections remain derived routing evidence.
- Bounded maintenance of an **already accepted derived navigation projection** is normal governance-evidence reconciliation during authorized state-changing work; do not require a repeated per-task permission line for that affected-only metadata update. Strict read-only mode or an explicit project/task prohibition on governance/metadata writes still wins.
- Still-material Follow-ups survive unrelated status refreshes; selection for a next task does not by itself delete them.
- Do not create `FINDINGS.md`, a Finding lifecycle, external tracker adapter, selector framework, scheduler, daemon, database, automatic repair, or target-project migration.
- Strict read-only work never mutates navigation projections or project controls.
- Overall behavior change is V1. Remote source/contract verification is V0; later lightweight local acceptance supplies V1 evidence.

## Review Focus

1. A verified route correction updates only the affected map entry and does not imply whole-map freshness.
2. An unchanged correct route causes no projection churn.
3. A non-blocking adjacent issue becomes a concise Follow-up without expanding or silently changing the current task.
4. A blocker is handled as a blocker, not hidden in Follow-ups.
5. A Follow-up selected for execution becomes explicit `CURRENT_TASK.md` scope before any repair and is not lost merely because it was selected.

### Task 6: Lightweight local V1 acceptance after source audit

**Precondition:** Web source audit accepts current A.

Use one disposable local test project and a supported unpublished candidate-loading path. Keep this lightweight: verify the active Plugin is the intended `0.5.0` candidate and that an older competing Engineering Governance authority is not being used. Do not build a dedicated eval platform unless acceptance itself reveals an ambiguity that cannot otherwise be resolved.

Run five natural behavior checks with fresh/reset test state as needed:

1. **Navigation correction:** an existing projection contains one intentionally wrong/stale route and one untouched route. A normal state-changing task requires the bad route to be resolved. After verification, the bad route is corrected and the untouched route remains unchanged without adding a per-task map-maintenance permission line.
2. **Navigation no-churn:** a correct route is used/verified; no projection write is produced merely for confirmation.
3. **Normal adjacent Follow-up:** a state-changing task encounters one small evidence-backed non-blocking adjacent problem. Current work is not expanded to repair it; a concise `CURRENT_STATUS.md / Follow-ups` item is retained.
4. **Next-task decision:** with a relevant Follow-up already in status, a natural "what should we do next?" request considers it together with normal priorities. If selected for execution, the resulting task scope explicitly includes it before repair; the Follow-up is not deleted merely because it was selected.
5. **Strict read-only:** read-only navigation/audit discovers an adjacent small problem; the result reports a Follow-up candidate, while navigation/status files remain unchanged.

Static V0 contract review, not extra runtime infrastructure, proves blocker-vs-Follow-up separation, preservation across unrelated status refreshes, and absence of external Findings machinery.

If a behavior is ambiguous, gather the smallest additional runtime/tool evidence needed for that case. Do not pre-build universal tracing or repeated-run infrastructure.

**Deliverable:** focused V1 evidence that the two user-visible governance behaviors work in the actual Plugin harness.

## Self-Review

- **Scope:** two capabilities only—navigation gets more accurate through verified use; small adjacent problems survive in current status long enough to influence next-task selection.
- **Control model:** no new control file. Status remembers; Task authorizes product/task mutation.
- **Navigation weight:** affected-only update to an already accepted projection, no whole-map rebuild, no write for unchanged routes, no per-task permission boilerplate.
- **Follow-up weight:** one optional status section, no registry, no external adapter, no selector, no lifecycle state machine.
- **Read-only:** reports candidates only; no control/map mutation.
- **Verification:** exact-A V0 plus five focused local behavior checks. No dedicated eval platform unless real ambiguity justifies it.
- **Execution environment:** remote Tasks 1–5 use GitHub-native operations; local acceptance starts only after Web source audit.

## Execution Method

Original method: native remote construction through Task 5, independent Web source audit, then lightweight local acceptance. This execution order is historical; the current integration task owns the active sequence and merge/release/test authority.
