# Selective capability composition

`project-governance` owns the task boundary and delivery. Each specialist owns a **method**, not another task authority. Compose only for a concrete unresolved dependency, then return the narrow result.

| Question | Route |
| --- | --- |
| What should this product screen do/look like? | `design` |
| Which API/state/module should own this behavior? | `solution-design` |
| Where is the accepted source or test? | `domain-navigation` |
| Why is this observed failure happening? | `incident-doctor` |
| Is parallel/delegated work worth its coordination cost? | `execution-orchestrator` |
| Does final evidence support a requested acceptance boundary? | `evidence-audit` |
| Does another context need an executable handoff? | `agent-handoff` |

The host chooses available tools and actual model/provider settings. External engineering frameworks can supply ideas; they do not silently override this project's selected task, source-of-truth, authority or runtime configuration.

Use the smallest useful composition. Frontend design and architecture may both be relevant, but neither must run for every UI change. Distinguish read-only observations, durable source documents, executable edits and host status; write each result only to its legitimate owner.

A cross-context Card states what the recipient needs to do, the already established authority reference and the delta; the receiver checks actual current permission.
