# Business-first development flow

Use this flow for normal governed product and business work:

1. Read applicable `AGENTS.md`, `CURRENT_STATUS.md`, and `CURRENT_TASK.md`, along with any relevant project authority. When Engineering Governance global routing is adopted, this normal project/repository work enters through Project Governance; route to narrower Skills only when their triggers apply.
2. Verify only the repository, ref/revision, runtime, and other baseline facts needed for the authorized work. When controls name Git identities, classify each identity under [Control identity and freshness](control-identity.md) before comparing values. A recorded transition/control parent is a relationship/provenance constraint unless the active task explicitly declares it as a locked/current/execution equality gate.
3. Before state-changing work, identify the selected task workspace (physical checkout/repository, branch or detached state, HEAD, and working-tree state) and establish its relationship to the task's authorized repository/ref/revision. A project-looking path, symlink, branch or folder name, archived copy, or detached checkout alone does not establish that relationship; an authorized, aligned non-main task worktree is valid.

   When the project uses multiple task workspaces, apply [Workspace lifecycle and closeout](workspace-lifecycle.md) before creating or selecting a conflicting writer workspace. Keep the check bounded to the active task: identify task-relevant predecessor writers whose write authority materially overlaps the proposed task, and establish their lifecycle, write-capability, and unique-work state. A broad capability or Domain label alone does not make two workspaces conflicting, and unrelated historical workspaces do not require routine full classification unless ambiguity, collision, unique work, lifecycle cleanup, or an explicit legacy-reconciliation task requires it.

   Preserve unknown staged, unstaged, untracked, or local-only work and do not mutate it merely to satisfy an execution card. If the selected workspace relationship, relevant predecessor disposition/write capability, or authoritative baseline/control is materially unresolved, stop and reconcile before continuing. Keep discovery task-bounded; expand beyond the selected workspace and relevant repository metadata only when ambiguity, unique work, lifecycle cleanup, or the task decision materially requires it.
4. Identify the affected Domain/capability from accepted semantic authorities already present in the project and any useful navigation projection. Use [Domain Navigation](../../domain-navigation/SKILL.md) when the responsible Domain/capability, authority, code location, symbol, runtime entry, dependency, or relevant test is unclear. Do not require a literal `DOMAIN_MAP.md` just because a template exists. Return the verified route to Project Governance; Domain Navigation does not become a second task authority.
5. Confirm the requested work remains within the active objective and scope. Ordinary evidence discovery that supports the accepted objective does not create a new task. A material objective or scope change requires updating `CURRENT_TASK.md` and re-authorization before continuing.
6. Before implementing source changes that add or change an owner, backend, or writer, identify the existing canonical authority for each affected state or behavior class. Before sharing behavior or splitting modules, apply [Code structure and canonical authority](code-structure.md). Reuse, extend, or explicitly replace an existing authority; reconcile independent writers instead of creating parallel truth. Keep structure decisions within the active task, then implement the smallest authorized product or business outcome.
7. Choose the lightest safe `V0`–`V3` verification tier and a separate verification cadence under [Verification tiers and cadence](verification-tiers.md). During construction, prefer focused checks appropriate to the tier. Group related acceptance findings into one bounded corrective where practical, then run broader affected regression once the corrective stabilizes. Reserve task-close and merge/release checks for the boundary whose claim they prove; do not rerun unrelated full suites after every small edit.
8. Update only controls whose owned, verified facts materially changed: durable rules in `AGENTS.md`, the current snapshot in `CURRENT_STATUS.md`, and the active authorization or handoff in `CURRENT_TASK.md`.
9. Leave a clean handoff or closeout with the baseline, changed paths, checks, unresolved evidence, and next authorized milestone stated accurately. If the project uses task branches/worktrees and project/task controls establish that the task or phase is terminal, require an explicit workspace disposition under [Workspace lifecycle and closeout](workspace-lifecycle.md): safely close obsolete workspace/branch state or retain it with a verified reason, release condition, and known write capability. A merge or other named lifecycle event alone does not prove terminal authorization or local closeout. Unknown work must remain preserved until its disposition is verified.

## Incident Doctor is on demand

If a real bug or failure appears and existing evidence is sufficient to decide and act safely, address it within the current authorization and verify the change; do not build Doctor or diagnostic infrastructure by default. If the problem is outside the authorized scope, reconcile and re-authorize the task first.

Enter [Incident Doctor](../../incident-doctor/SKILL.md) only when a real failure, unexplained behavior, or unsafe ambiguity blocks safe progress and an evidence gap prevents the needed decision. Keep routine feature delivery separate from diagnostic infrastructure work; add only the minimum diagnosis authorized for the blocked question. If Doctor needs Domain Navigation to locate evidence, return to Doctor after that bounded route is established.
