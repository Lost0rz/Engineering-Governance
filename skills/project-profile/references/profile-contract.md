# Project Profile — compact derived context

`PROJECT_PROFILE_CLASS: DERIVED_PROJECT_CONTEXT`

The Profile is a **navigation aid**, not a workflow controller, approval record or substitute for authoritative source. Create or refresh it only when requested or when an actual context-recovery need exists.

## Ground and select facts

1. Verify each retained fact against current source, accepted product/design/API authority, actual host/runtime evidence, or an explicit current user decision.
2. Treat memory, older summaries, prior Profiles and handoff notes as *discovery hints*, not proof of current project truth.
3. Prefer durable project purpose, major domains, real source pointers, enduring constraints, current runtime topology when stable, and the owning authority for a decision.
4. Keep changing task/PR/CI status and sensitive credentials in their real owners rather than duplicating them in the Profile.
5. Remove stale, unverified, repeated or over-specific facts; preserve useful links rather than copying long documents.

## Structure and freshness

Use [the Profile template](../assets/templates/PROJECT_PROFILE.md) for compact sections and primary/mirror roles. Each claim should be traceable to its real authority and sufficiently durable for context recovery. Explain an unresolved important fact separately rather than presenting it as settled.

On a refresh, validate only what is retained or newly added. A meaningful architecture/product change may make the Profile stale, but ordinary commits and progress updates do not by themselves require rebuilding it.

`AGENTS.md` retains project-specific normative constraints; the installed Engineering Governance plugin owns shared workflow. The Profile neither changes their authority nor activates a host permission.
